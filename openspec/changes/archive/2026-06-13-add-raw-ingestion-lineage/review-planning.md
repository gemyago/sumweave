## 2026-06-13 Dedicated planning review

Verdict: revise before implementation.

### Findings

1. Add explicit validation/failure acceptance criteria for all lineage records, not just ingestion runs.
   - `proposal.md` promises validation coverage for the lineage model as a whole, and `tasks.md` task `1.1` says validation applies to `IngestionRun`, `RawVenuePayload`, `NormalizationRun`, and `DataBatch`.
   - `specs/data-layer/spec.md` only defines an explicit rejection path for ingestion runs (`missing identity or source`). The other lineage entities only have happy-path/idempotency scenarios.
   - This leaves required behavior underspecified for missing stable IDs and missing/unknown parent links on raw payload, normalization, and batch writes.

2. Reconcile the promised `batch/run` audit scope with the batch-only read contract.
   - `proposal.md` says read access should let operators `audit a batch/run`.
   - `tasks.md` task `3.2` and the `Lineage Audit And Replay Lookup` requirement in `specs/data-layer/spec.md` only define batch-centered lookup and replay behavior.
   - Either narrow the proposal/design wording to batch-scoped reads or add explicit acceptance criteria and tasks for direct run-level audit lookups.

3. Define the ordering key for multi-payload audit results.
   - `design.md` and `specs/data-layer/spec.md` allow a normalization run to link to `one or more raw payloads`.
   - The spec requires batch audit reads to return linked raw payload metadata `in deterministic order`, but it does not say whether that order is by received time, payload identity, insertion order, or another stable key.
   - The implementation and tests need that ordering rule up front to avoid accidental contract drift.

### Chunking recommendation

- Complexity: moderate; this is still a contained `runtime/data` change, but the validation and read-contract gaps should be fixed before implementation starts.
- Sequencing: sequential; each parent task depends on the contracts and schema choices established before it.
- Recommended chunks after the planning fixes:
  1. Parent task 1 (`1.1-1.2`) as chunk `lineage-contracts`.
  2. Parent task 2 (`2.1-2.2`) as chunk `gorm-lineage-persistence`.
  3. Parent task 3 (`3.1-3.2`) as chunk `batch-audit-replay`.
