## Context

`finance/internal/providers/sync_orchestrator.go` already requires a `TargetWindowPolicy`, but there is no concrete implementation in the repo today. A repo-wide search only finds:

- the consumer-owned interface in `sync_orchestrator.go`
- autogenerated mocks in `mocks_test.go`
- orchestrator tests that stub the policy

So target-window planning is specified as a seam, but not yet delivered as behavior.

We do already have enough direction to close that gap:

- `docs/finance-provider-sync-architecture.md` says sync should refresh the recent window and catch up when prior coverage is older.
- `openspec/changes/archive/2026-06-26-clarify-provider-sync-attempt-journal/` changed the journal semantics so planning receives the latest appended state directly, including failed latest attempts.
- That archived change also left one intentional follow-up question open: what the first target-window policy should do when the latest state is failed.

The latest user guidance now makes the broader behavior clear enough for a first implementation:

- if there is no prior state, start with a wider 3-year backfill
- if the prior checkpoint is within the last 30 days, refresh the last 30 days
- if the prior checkpoint is older than 30 days, catch up from that checkpoint until now

The remaining design job is to define what "prior checkpoint" means for the latest succeeded row versus the latest failed row.

## Goals / Non-Goals

**Goals:**

- Implement the first concrete provider-sync target-window policy in `finance/internal/providers/`.
- Keep the policy pure: input is `now` plus the latest loaded state, output is one target window or an error.
- Preserve the requested behavior of 3-year initial backfill plus 30-day recent refresh.
- Make latest failed attempts resumable without special orchestrator glue.
- Fail clearly when the loaded state window is structurally invalid.

**Non-Goals:**

- Implement or change window chunk splitting.
- Add provider fetch, diff, apply, or run persistence behavior.
- Add scheduler, API, or UI wiring.
- Add configurable per-provider or per-connection lookback periods in this first slice.
- Implement full-history or user-driven history selection in this first slice.

## Decisions

1. Add one dedicated target-window policy component in `finance/internal/providers/`.

   The policy should be a small component that satisfies the existing `TargetWindowPolicy` interface directly. This keeps the orchestration dependency consumer-owned and avoids pushing window-selection logic into `SyncOrchestrator`.

   Alternative considered: inline the default behavior inside `SyncOrchestrator`. Rejected because the current seam is already the right boundary, and the repo explicitly prefers focused components over growing orchestration glue.

2. Use a 3-year initial backfill window for fresh runs.

   When no prior state exists, the first implementation should plan `[now-3y, now]`, using calendar-year subtraction semantics through `AddDate(-3, 0, 0)`. This matches the requested near-term behavior while leaving room for a later move to full-history or user-driven scope.

   Alternative considered: jump directly to entire-history sync. Rejected for now because the requested direction explicitly treats 3 years as the current bounded default and defers broader history control to later work.

3. Derive one prior checkpoint from the latest loaded state before applying the age rule.

   The policy should use the latest loaded state exactly as the journal seam returns it:

   - `state == nil` -> no checkpoint exists
   - `state.SucceededAt != nil` -> treat `state.Window.End` as the prior checkpoint
   - `state.SucceededAt == nil` -> treat `state.Window.Start` as the retry checkpoint for the failed attempted chunk

   This keeps the attempt-journal direction intact and avoids reconstructing older success state inside orchestration. It also makes the user rule apply uniformly to one derived checkpoint regardless of outcome.

4. Apply the age-based planning rule to that checkpoint.

   Let:

   - `initialStart = now.AddDate(-3, 0, 0)`
   - `recentStart = now.AddDate(0, 0, -30)`

   The target end is always `now`, and target start is:

   - Fresh run: `initialStart`
   - Prior checkpoint after or equal to `recentStart`: `recentStart`
   - Prior checkpoint before `recentStart`: that checkpoint

   This achieves the intended behavior:

   - fresh connections get a bounded historical backfill instead of only a recent refresh
   - recently synced connections still refresh the last 30 days
   - older checkpoints catch up continuously from where sync history last left off
   - failed windows older than the recent window are retried before newer chunks
   - failed windows inside the recent window naturally fall back to the normal 30-day refresh

5. Reject structurally invalid loaded windows instead of guessing.

   If a non-nil latest state carries a zero start, zero end, or a window where `End` is not after `Start`, the policy should return a bounded planning error. Silent fallback to the rolling baseline would hide journal corruption or bad persistence mapping and make sync recovery less explainable.

   Alternative considered: ignore invalid state and proceed with the baseline. Rejected because it hides data-quality issues in the one seam now responsible for interpreting latest-attempt history.

6. Keep the policy chunk-agnostic.

   The target-window policy returns exactly one target window. It does not split that window, reorder work, or inspect cumulative stats. Chunk sizing and oldest-first execution remain the responsibility of `WindowChunkPolicy` plus `SyncOrchestrator`.

## Risks / Trade-offs

- [A 3-year fresh backfill may still be too shallow for some accounts] -> Accept for now because the requested direction explicitly treats this as a revisitable bounded default.
- [A fixed 30-day recent-refresh rule may later prove too rigid for some providers] -> Accept for now; if a real provider constraint appears, add a follow-up OpenSpec change rather than speculative configuration.
- [Planning now surfaces invalid journal windows as errors] -> Accept because explicit failure is safer than syncing the wrong range.

## Migration Plan

1. Add focused target-window policy tests in `finance/internal/providers/` for 3-year fresh runs, recent 30-day refresh, older-checkpoint catch-up, failed-latest retry behavior, and invalid-state failures.
2. Implement the concrete policy component and keep it local to `finance/internal/providers/`.
3. Update the finance-management spec delta so the 3-year initial backfill plus checkpoint-age planning rules are explicit acceptance criteria.
4. Update adjacent finance sync documentation if needed so the failure-resume behavior is documented in the same terms as the implemented policy.

Rollback is removing the new policy component and reverting its focused tests and planning artifacts. No persistence migration is required for this change.

## Open Questions

- None for this first implementation. Entire-history sync and user-driven scope can stay separate follow-up changes if they become product requirements.
